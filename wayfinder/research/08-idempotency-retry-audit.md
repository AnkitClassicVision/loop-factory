# Idempotency + retry audit — podcast department runtime

Read-only audit. Ticket: `wayfinder/tickets/08-idempotency-retry-audit.md`. No code
executed; findings are from static reading of every file in
`departments/podcast/runtime/`, `factory/manager.py`, `factory/heal_ladder.py`,
`factory/human_in_the_loop.py`, `factory/launch.py`, the systemd unit/timer,
and live-state SHAPE inspection (line counts, key names, duplicate-row counts —
no content bodies) of `departments/podcast/state/*`.

## Trigger topology (who can fire the chain twice)

`departments/podcast/runtime/podcast_daily.sh` is the sole entry point, run by
`departments/podcast/runtime/systemd/podcast-daily-department.timer`
(`OnCalendar=*-*-* 07:00:00`, `Persistent=true`, `RandomizedDelaySec=120`) via
`podcast-daily-department.service` (`Type=oneshot`, **no `Restart=` directive**).

- systemd itself will not run two overlapping instances of the same oneshot
  unit from its own timer; `Persistent=true` means a missed 07:00 tick (host
  was off) fires once on next boot — a legitimate double-trigger vector if a
  human then also manually re-runs `podcast_daily.sh` the same day.
- The script itself has **no pidfile/mutex** (`podcast_daily.sh:1-49`). Nothing
  in the script stops a manual second invocation from running concurrently
  with a systemd-triggered one. The only concurrency guard anywhere in the
  chain is the `fcntl` lock in `departments/podcast/runtime/record.py`
  (`records_lock`, `record.py:33-56`), and it is applied inconsistently (see
  table).
- `set -euo pipefail` (`podcast_daily.sh:7`) means any node that actually exits
  non-zero halts the rest of that day's chain. `dag_supervisor.py` exit code 2
  is explicitly carved out as a valid alarm, not a failure
  (`podcast_daily.sh:34-40`).

## Ranked gap list — what ticket 15 must close

1. **`factory/manager.py` writes `STATE.json` / `runs.jsonl` / `heartbeats.jsonl` without the `record.records_lock` that protects the same files elsewhere.** This is the only genuine unlocked-write race in the department: under concurrent invocation (double systemd tick + manual re-run, or any future scheduler change that permits overlap), the two epoch-derivation code paths (`record.write_record` vs. `manager.py act()`) can race on the identical files with no error raised — last `os.replace` silently wins. Fix: route `manager.py`'s STATE/runs/heartbeat writes through `record.records_lock` (or a single shared epoch-fencing helper), and add a concurrency test analogous to `test_record_writer_times_out_while_shared_lock_is_held` but for `manager.py`.
2. **`manager.py`'s own escalations have no fingerprint/marker dedup**, unlike `escalate_outbox.py`. A persisting breach (`run_failed`, `held_recipient_mismatch`, budget-near, etc.) re-appends a fresh escalation packet to `decisions_outbox.jsonl` on every cycle it remains true, and a crash-then-retry has no way to tell "new occurrence" from "same occurrence, replayed." Fix: give manager-originated escalations the same durable-marker check `escalate_outbox.py` already has and already proves safe under an injected crash.
3. **`pipeline_sensor.py`, `publish_verifier.py`, `manifest_sensor.py` never call `record.write_record`.** They have no run receipt of any kind, so a crash (or, currently, a permanently-missing source directory) is indistinguishable from "ran and found nothing" in `runs.jsonl`/`heartbeat`. Fix: give these three nodes the same epoch-fenced receipt `sense_estate.py`, `dag_supervisor.py`, `compare_charter.py` already have.
4. **`factory/human_in_the_loop.py`'s `_save()` is the one non-atomic JSON/JSONL writer in the department** — a crash mid-write can corrupt `approval_queue.jsonl` with no fail-closed handling downstream. Fix: switch to the same temp-file + `os.replace` pattern used everywhere else (`record.atomic_write_json`).
5. **`observations.jsonl` (and, once populated, `heals.jsonl`) grow without bound and without dedup on replay.** Confirmed live: 11,166 lines / ~7 MB with hundreds of exact-duplicate rows per `(sensor, subject)` key, because four of the five sensor nodes append unconditionally on every trigger. `compare_charter.py` already absorbs this correctly for classification purposes (latest-row-per-key), so this is not currently a correctness bug — but there is no rotation/compaction/retention node anywhere in the department, so the file will keep growing indefinitely. Fix: decide a retention/compaction policy before this becomes a real disk or read-latency problem.
6. **`heal_apply.py`'s attempt-counter reservation and its receipt append are two separate, non-transactional writes** (`heal_attempts.json` vs. `heals.jsonl`). A crash between them silently consumes one of the two daily attempts for that `fingerprint:playbook_id` with no visible record of why. Currently inert in shadow mode, but must be fixed before any live promotion. Fix: reserve the attempt and append the receipt atomically (or reverse the order and make the receipt the thing that consumes the budget).
7. **The self-heal ladder (`factory/heal_ladder.py`'s `HealLadder` class, and `heal_select.py`/`heal_apply.py`/`heal_verify.py` generally) is not wired into `podcast_daily.sh` or `factory/manager.py` at all.** Nothing in the automatic daily trigger chain currently calls any of the three heal nodes or the L1/L2/L4 ladder the README and `heal_ladder.py`'s own docstring describe. Ticket 15 needs to either wire this in or explicitly scope it out — right now an open, healable incident sits in `incidents.json` with no automatic path to a heal attempt.
8. **`dag_supervisor.py`'s direct appends to `incident_candidates.json` are only deduped by `compare_charter.py`'s next successful overwrite.** If the chain aborts between the two (e.g., a node between them exits non-zero and `set -e` halts the script), duplicate `dag_supervisor`-authored incident-candidate entries persist until the next full successful run reaches `compare_charter.py` again. Low severity today (self-heals on the next good run) but worth a named test.

## What was not verified

- Whether systemd genuinely coalesces/queues a second start of the same oneshot unit while one is active was not tested live (read-only audit; no service was started). This is standard systemd unit-activation behavior for a named unit, not something specific to this repo's config, so it is asserted from systemd semantics rather than an executed check here — flagged as `unknown` in the strict sense the ticket asked for.
- Whether an OS-level power-loss (vs. a process crash) between an `open("a").write()` and the OS flushing that page to disk could lose an already-"durable" line (`observations.jsonl`, `decisions_outbox.jsonl`, `heals.jsonl`, `runs.jsonl`) was not tested — none of these appends call `fsync` except `record.write_record`'s `runs.jsonl` write (`record.py:141-143`) and its `heartbeat` write (`record.py:169-170`). Everything else is process-crash-safe by the evidence above but not proven power-loss-safe.
- The `.worktrees/fix-estate-watchdog` and `.worktrees/wire-drift-check` directories in this repo suggest related work may already be in flight on the estate watchdog / drift-check surface; this audit did not read those worktrees (out of scope for a read-only audit of the current checkout) but ticket 15 should check whether they already address any of the gaps above before duplicating work.
