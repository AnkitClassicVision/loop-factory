## Same-entity, no-sync collisions (worst 5)

1. **Referral ledger fork, same repo.** `podcast/episodes/REFERRALS.json` (`asks[]`, 3 real entries incl. Gina Wesley) vs `podcast/episodes/_referrals.json` (`asked[]` empty, `received[]` one placeholder) — near-identical filenames, disjoint reader/writer sets (`candidate_ingest.py`/`funnel_status.py`/`loop_runner.py` read the capitalized file; `inbox_review.py` reads/writes the underscore file), zero shared code path, zero reconciliation.
2. **Gina Wesley referral, stuck.** Gmail thread `19fb98a243313466` (ask sent 2026-07-31) is the only evidence of the ask; `REFERRALS.json` mirrors it as `state:"asked"` but the file's own embedded note says the consumer that would advance it (`loop_runner.assemble_world`) hardcodes `referrals: []` and never reads this file — so the state is structurally unable to progress past "asked." No corresponding entry exists in `_referrals.json` or `episode.json`. HubSpot's `podcast_status` property tracks guest funnel stage, not referral-ask state, so it is not actually a third copy of *this* fact — confirmed absence, not confirmed presence, of a third store for Gina specifically.
3. **Guest funnel stage, two systems.** `podcast/episodes/*/episode.json` `stage`/`stage_timestamps` (local, per-episode) vs HubSpot contact property `podcast_status` (external) both claim to be the guest's funnel stage of record. `tracker.py`/`inbox_review.py` re-pull HubSpot fresh each run rather than trusting the local file, but `funnel_status.py`/`candidate_ingest.py` read only the local `stage` — no persisted join, so a HubSpot-side status change is invisible to the local-file readers until the next inbox-review pass touches that specific guest.
4. **Referral candidate ledger, different keys.** `podcast/episodes/_loop_receipts/referral-flywheel-candidate-ledger.json` keys by HubSpot `contact_id` (1 entry, `"carded"`); `REFERRALS.json` keys by `guest_id` (3 entries). No field in either file maps one key space to the other, so nothing can programmatically tell whether the carded contact is any of the three pending asks.
5. **Gmail processed-cursor fork, hubspot-daily-2.** `state/gmail_context_sync_state.json` (stale since 2026-06-23) vs `state/inbound-context-sync-state.json` (current, updated 2026-08-03) both maintain independent "which Gmail message IDs have been processed" ledgers for overlapping lanes. This is PROCESS state, not entity state, but it's the same failure shape: two cursors for one mailbox, no cross-check, and loop-factory's own `decisions_outbox.jsonl` is already escalating stale-receipt findings against files in this cluster.
