## 2. `frequency.py` deep-read

**File:** `kernel/gateways/frequency.py`. **Scope: per-department, not estate-global.**

- **Key:** whatever strings the caller passes as `person` and `org` — the module does no validation of what those strings mean (email? name? platform?). No canonicalization (no case-folding, no email normalization).
- **Window:** `PERSON_WINDOW_S = 30 * 86400` (≤3 touches per `person` per 30 days), `ORG_WINDOW_S = 7 * 86400` (≤1 distinct `person` per `org` per 7 days). Comment confirms a prior bug where these were seconds, not days — since fixed.
- **Ledger location:** `FrequencyService(freq_ledger)` is constructed inside `kernel/lock_service.py`, which is built per call to `kernel/bridge.py:load_kernel(state_dir)`. The ledger path is hard-coded as `state_dir / "kernel" / "frequency.jsonl"`, and `state_dir` is always a specific department's state dir (`departments/<dept>/state`). **There is no shared/estate-level `FrequencyService` instance anywhere in the codebase.** Each department gets its own empty ledger file and its own 3/30-day, 1/7-day counters, isolated from every other department.
- **Callers today (grep-verified, excluding worktrees/pycache):** exactly one real call site — `departments/social/runtime/kernel_bridge.py:116` (`request_dispatch_token` → `kernel.request_send`). It passes `person=f"surface:{surface}"` and `org=f"surface:{surface}"` — i.e. **it is not being used to cap touches to a human at all**; it caps posts per social-media surface (linkedin_mybcat, facebook_mybcat, etc.). `departments/podcast` in loop-factory has zero call sites into `request_send`/frequency at all. So today, frequency.py's documented "≤3 touches per person" semantic has never been exercised against an actual external human — the one live caller repurposed it for a different concept.

## 3. Concrete collision scenarios (worst three)

1. **Podcast prospecting vs. podcast manual guest email — same repo, no shared bucket.** `prospecting.py` keys cadence as `(loop_id="podcast-prospecting"-ish, target_id="hubspot:{contact_id}")` while `send_guest_email.py` keys as `(loop_id="manual-one-shot-email", target_id="email:{addr}")`. Both go through the same `outbound.dispatch()` gateway and the same `should_act` cadence check, but because the `(loop_id, target_id)` pair differs for the same physical optometrist, the 4-day cadence floor and attempt cap **do not see each other**. An operator running `send_guest_email.py` today has no automatic signal that the automated prospecting loop touched the same OD yesterday.

2. **Podcast outreach vs. hubspot-daily-2 `/daily` sales agent — different repos, different databases, no join.** Podcast's `Ledger`/`should_act` cadence lives in the podcast repo's own state; hubspot-daily-2's suppression (`scope_suppression_pass`, `daily_agent_sends` SQLite table) lives entirely in its own repo. Both write into the **same HubSpot portal** (confirmed: both use `HUBSPOT_BCC=23344341@bcc.hubspot.com`, so both post notes/engagements to the same contact record), which means the identity key needed to join them (`hubspot_contact_id`) already exists on both sides — but neither system queries the other's ledger or the shared HubSpot contact timeline before sending. A podcast-guest OD who is also a sales prospect can receive a podcast outreach email Monday and a `/daily` cold-touch email Tuesday with zero cross-check.

3. **loop-factory `departments/social` vs. anything else — frequency.py is scoped to the wrong entity.** Even inside loop-factory, `frequency.py`'s only live caller treats the recipient key as `surface:{platform}`, not a human identity. So even if podcast or another department were wired into the same kernel frequency gate tomorrow, it would not collide-protect against social's usage today — social's "person" cap is really a platform-post-rate cap, and a real cross-department arbitration decision needs frequency.py's semantics either fixed at that one call site or given a second, human-keyed instance.

## 4. Identity-resolution state

**No automated identity-resolution join exists across these systems today.** The technical precondition is present — podcast and hubspot-daily-2 share one HubSpot portal and both use `hubspot_contact_id`/email as their internal key, and podcast's `prospecting.py`/`referral_touch_automation.py` already resolve `email -> hubspot contact_id` via HubSpot search at draft time — but nothing reads across the two systems' ledgers (podcast's file-based `Ledger`, hubspot-daily-2's SQLite `daily_agent_sends`, loop-factory's per-department `frequency.jsonl`) before authorizing a send. The only place all channels converge is the shared BCC mailbox (`23344341@bcc.hubspot.com`), which is a forensic log, not a live gate.

## Notes / surprises for the follow-on decision ticket

- `frequency.py`'s design (per-person/per-org caps, 30d/7d windows) is exactly the shape condition 6 needs, but it is (a) instantiated per-department with no shared ledger, and (b) its one real caller doesn't feed it human identities at all. Promoting it to cross-department duty needs either a new estate-level `FrequencyService` instance with a shared ledger path, or a wrapper the kernel calls into for every `request_send` regardless of department.
- Three independent send-authorization stacks exist (loop-factory kernel gateways, podcast repo's `outbound.dispatch`, hubspot-daily-2's `/daily` agent + SQLite), each internally fail-closed and well-gated, but with **zero shared state between them**. Any cross-department cadence cap has to either bridge all three or accept it only covers loop-factory-native departments (which today send nothing real — podcast/social are shadow, podcast's live sends run entirely outside loop-factory).
- `send_guest_email.py`'s sibling one-off scripts (`send_herrera_email.py`, `send_herrera_followup_email.py`, `send_herrera_launch_email.py`) are a growing class of manual one-shot senders, each presumably minting its own `loop_id`/`target_id` pair — worth enumerating fully before condition 6 locks a design, since every new one-off script is a new cadence bucket that doesn't see the others.
